# Express TypeScript User API

A RESTful backend API built with **Node.js, Express, and TypeScript** for managing users in memory.

The project is designed as a small learning-oriented backend that demonstrates separation of responsibilities through models, repositories, services, controllers, routes, and middleware.

## Features

* User CRUD operations
* In-memory user storage
* TypeScript with strict type checking
* Layered architecture
* Express middleware
* Centralized error handling
* Health check endpoint
* Environment-based server port configuration

## Tech Stack

* **Node.js**
* **Express**
* **TypeScript**
* **tsx**
* **npm**

No database or ORM is used. User data is stored in memory and is reset whenever the server restarts.

### Architecture

The application follows a layered architecture:

```text
HTTP Request
     │
     ▼
   Routes
     │
     ▼
 Controllers
     │
     ▼
  Services
     │
     ▼
 Repositories
     │
     ▼
    Data
```

Each layer has a specific responsibility:

* **Routes** — Define HTTP endpoints and connect them to controllers.
* **Controllers** — Handle HTTP requests and responses.
* **Services** — Contain application and business logic.
* **Repositories** — Encapsulate access to the in-memory data.
* **Data** — Contains the temporary user collection.
* **Models** — Define TypeScript contracts for application entities.
* **Middlewares** — Handle cross-cutting HTTP concerns such as errors.
* **`app.ts`** — Configures the Express application.
* **`server.ts`** — Starts the HTTP server.

## User Model

Users have the following structure:

```typescript
interface User {
  id: number;
  name: string;
  email: string;
  age: number;
}
```

## API Endpoints

### Health Check

```http
GET /health
```

Returns the current API status.

Example response:

```json
{
  "status": "ok"
}
```

### Get All Users

```http
GET /api/users
```

Returns all users currently stored in memory.

### Get User by ID

```http
GET /api/users/:id
```

Example:

```http
GET /api/users/1
```

Returns the requested user or a `404` response if the user does not exist.

### Create User

```http
POST /api/users
```

Request body:

```json
{
  "name": "Ana Torres",
  "email": "ana@example.com",
  "age": 28
}
```

Returns the newly created user with a generated ID.

The service validates the required fields and prevents duplicate email addresses.

### Update User

```http
PATCH /api/users/:id
```

Example request:

```http
PATCH /api/users/1
Content-Type: application/json
```

```json
{
  "age": 26
}
```

Updates the specified fields of an existing user.

### Delete User

```http
DELETE /api/users/:id
```

Example:

```http
DELETE /api/users/1
```

Returns `204 No Content` when the user is successfully deleted.

## Getting Started

### Prerequisites

Make sure you have installed:

* Node.js
* npm

### Installation

Clone the repository and install the dependencies:

```bash
npm install
```

### Development

Start the development server with automatic TypeScript reloading:

```bash
npm run dev
```

The server runs on:

```text
http://localhost:3000
```

### Build

Compile the TypeScript source:

```bash
npm run build
```

The compiled files are generated in the `dist/` directory.

### Production

After building the project:

```bash
npm start
```

## Environment Variables

The server uses the `PORT` environment variable when provided.

Example:

```env
PORT=4000
```

If no port is specified, the application uses `3000` by default.

## Error Handling

Application errors are handled through a centralized Express error middleware.

Errors generated by the service layer are passed through the request pipeline and transformed into JSON HTTP responses.

Example:

```json
{
  "message": "Email is already in use"
}
```

## Data Persistence

This project intentionally uses an in-memory array instead of a database.

As a result:

* Data is lost when the server restarts.
* No database configuration is required.
* The repository layer isolates data access from the rest of the application.

This makes the project suitable for learning and for demonstrating the separation between application layers before introducing persistent storage.
